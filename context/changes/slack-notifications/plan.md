# Slack Notifications — Soon Badge + Model Stub

## Overview

Add a `SlackNotification` model stub and surface a "Soon" Slack card in the
connections provider grid. This lays the backend foundation for future Slack
alerting and makes the upcoming feature visible to users — without any live
Slack API calls.

## Current State Analysis

The connections page (`/connections/`) already hosts a provider selector grid
with five cards: PostgreSQL (available) and MySQL, Amazon S3, BigQuery, and
Snowflake (all "Soon" / disabled). The grid uses `repeat(5, 1fr)`.

`monitor/models.py` defines four models — `Connection`, `Rule`, `CheckRun`,
`RuleResult` — with no notification-related model present. Four migrations
exist; the next will be `0005_slacknotification.py`.

There is no notifications settings page, no notifications URL, and no
notifications view in the current codebase.

### Key Discoveries:

- `connection_list.html:~17` — grid is `repeat(5, 1fr)`; must change to `repeat(6, 1fr)` for the sixth card
- `connection_list.html:~42,62` — `.provider-card.disabled` and `.badge-soon` CSS already defined; the new card needs no additional styles
- `monitor/models.py:1–185` — no existing `SlackNotification`; `settings.AUTH_USER_MODEL` defaults to `auth.User`
- `monitor/migrations/` — 4 migrations; new one will be `0005_slacknotification.py` (auto-generated)

## Desired End State

After this change:
- `GET /connections/` renders a six-card provider grid with Slack as the sixth card, "Soon" badge, disabled/greyed appearance — matching MySQL/S3/BigQuery/Snowflake
- `SlackNotification` exists in the database (migration applied cleanly), with fields `id`, `user` (nullable FK → `auth.User`), `webhook_url` (CharField, blank), and `enabled` (BooleanField, default=False)
- All existing tests continue to pass; two new tests are green

### Key Discoveries:

- Slack icon: standard Slack hashtag/grid SVG, Slack-brand purple `#4a154b` tint — same icon style as the other "Soon" cards
- Nullable `user` FK: `null=True, blank=True` on a new model is a safe migration with no data risk

## What We're NOT Doing

- No Slack API calls, no webhook dispatch, no real notifications
- No notifications settings page (deferred to S-13, which will add email; both will share a single page)
- No admin registration for `SlackNotification`
- No form or view for `SlackNotification`
- No encryption of `webhook_url` (it's a stub field; encryption deferred to when the feature activates)
- No changes to `monitor/views.py`, `monitor/urls.py`, `monitor/forms.py`, `data_pulse/settings.py`, or `templates/base.html`

## Implementation Approach

Three narrow, sequential phases:
1. Add `SlackNotification` to `models.py`, generate migration.
2. Add the Slack card to `connection_list.html` and bump the grid column count.
3. Write two tests (model creation + UI card presence) and run the full suite.

## Phase 1: SlackNotification Model + Migration

### Overview

Add `SlackNotification` to `monitor/models.py` and auto-generate the migration.
The model is a minimal stub — no form, no admin, no view.

### Changes Required:

#### 1. SlackNotification model

**File**: `monitor/models.py`

**Intent**: Append a new `SlackNotification` model after `RuleResult`. This
model records a user's Slack webhook destination and acts as a feature flag
(`enabled=False` until the integration is live).

**Contract**:

| Field | Type | Constraints |
|---|---|---|
| `id` | AutoField (implicit) | PK |
| `user` | ForeignKey → `settings.AUTH_USER_MODEL` | `on_delete=CASCADE`, `null=True`, `blank=True`, `related_name='slack_notifications'` |
| `webhook_url` | CharField | `max_length=500`, `blank=True` |
| `enabled` | BooleanField | `default=False` |
| `created_at` | DateTimeField | `auto_now_add=True` |
| `updated_at` | DateTimeField | `auto_now=True` |

`__str__` returns `f'SlackNotification(user={self.user_id}, enabled={self.enabled})'`.

#### 2. Migration

**File**: `monitor/migrations/0005_slacknotification.py`

**Intent**: Auto-generated by `python manage.py makemigrations`. Do not
hand-write this file — run the command and commit the output.

**Contract**: Migration must depend on `('monitor', '0004_...')` (the last
existing migration). Verify with `python manage.py showmigrations monitor`.

### Success Criteria:

#### Automated Verification:

- Migration generates without errors: `python manage.py makemigrations --check` passes after manual `makemigrations` run
- Migration applies cleanly: `python manage.py migrate --run-syncdb` (or `migrate`)
- No import errors: `python manage.py check`

#### Manual Verification:

- `python manage.py shell -c "from monitor.models import SlackNotification; print(SlackNotification._meta.fields)"` lists expected fields

**Implementation Note**: After completing this phase and all automated verification passes, pause here for manual confirmation before proceeding.

## Phase 3: Tests

### Overview

Add two focused tests: one confirming `SlackNotification` can be created with
default values, one confirming the Slack card appears in the connections page
HTML.

### Changes Required:

#### 1. Model test

**File**: `monitor/tests.py` (append to existing test file)

**Intent**: Assert that `SlackNotification(enabled=False)` is the default, and
that the model saves and retrieves correctly with no user assigned.

**Contract**: Create a `SlackNotification()` with no arguments (relying on
defaults). Assert `enabled == False`, `webhook_url == ''`, `user is None`.
Use `TestCase`.

#### 2. UI card test

**File**: `monitor/tests.py` (append)

**Intent**: Assert that the connections page HTML includes the text "Slack" and
the "Soon" badge, so a regression test catches accidental removal.

**Contract**: Use `self.client.get(reverse('monitor:connection_list'))`.
Assert `response.status_code == 200`, `b'Slack' in response.content`, and
`b'badge-soon' in response.content`. The view requires login — use
`self.client.force_login(user)` with a test user.

### Success Criteria:

#### Automated Verification:

- Tests pass: `python manage.py test monitor`
- No regressions in existing suite

#### Manual Verification:

- Test output shows `OK` with the two new tests listed
