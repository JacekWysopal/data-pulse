# Slack Notifications — Plan Brief

> Full plan: `context/changes/slack-notifications/plan.md`
> Research: `context/changes/slack-notifications/research.md`

## What & Why

Surface Slack as an upcoming notification channel in the UI and create the
backend model stub that will activate when the Slack API integration lands.
This makes the roadmap intent visible to users without shipping any live
functionality.

## Starting Point

The connections page already shows a provider selector grid with five cards
(PostgreSQL available; MySQL, S3, BigQuery, Snowflake as "Soon"). There is no
notification model or notifications page in the codebase today. The grid CSS
and "Soon" badge styles are already in place.

## Desired End State

`GET /connections/` shows a six-card provider grid with Slack as the sixth
card — greyed out, "Soon" badge, non-interactive — identical to the MySQL
and S3 cards. The `SlackNotification` table exists in the database, ready for
a future view/form to activate it.

## Key Decisions Made

| Decision | Choice | Why (1 sentence) | Source |
|---|---|---|---|
| `user` FK on model | Nullable FK (`null=True, blank=True`) | Avoids a future migration and creates no schema risk on a new model | Plan |
| Field name | `enabled=False` | Idiomatic Django over `disabled=True`; consistent with boolean field conventions | Plan |
| Badge placement | Connections page provider grid (6th card) | Only existing UI that already shows "Soon" badges; no new page needed | Research |
| Grid layout | `repeat(6, 1fr)` | Keeps single-row layout; `auto-fill` is more flexible but unnecessary for a fixed set | Research |
| Notifications settings page | Defer to S-13 | No page exists today; S-13 (email) will create it and Slack reuses the same page | Plan |
| Slack API calls | None | Stub only; activation is a future change | Change.md |
| Migration | Auto-generated via `makemigrations` | Never hand-write migrations; let Django derive the dependency chain | Plan |

## Scope

**In scope:**
- `SlackNotification` model with `id`, `user` (nullable FK), `webhook_url`, `enabled`, `created_at`, `updated_at`
- Migration `0005_slacknotification.py` (auto-generated)
- Slack "Soon" card appended to the provider grid in `connection_list.html`
- Grid column count updated from 5 to 6
- Two tests: model defaults, UI card presence

**Out of scope:**
- Slack API calls or webhook dispatch
- Notifications settings page
- Admin registration for `SlackNotification`
- Form or view for `SlackNotification`
- `webhook_url` encryption (deferred to activation)

## Architecture / Approach

Two files change: `monitor/models.py` (new model class) and
`templates/monitor/connection_list.html` (one CSS rule + one card block).
A third file — the migration — is auto-generated by Django. The change is
purely additive: no existing code is modified beyond the column count and an
appended HTML block.

## Phases at a Glance

| Phase | What it delivers | Key risk |
|---|---|---|
| 1. SlackNotification Model + Migration | New DB table, model fields verified | Migration dependency order (auto-generated handles this) |
| 2. Slack Card in Provider Grid | Visual "Soon" badge on /connections/ | Grid wrapping if column count not updated |
| 3. Tests | Model default + UI card regression coverage | View requires login — force_login needed in test |

**Prerequisites:** None — this change has no upstream dependency.  
**Estimated effort:** ~1 session; 2 files + 1 auto-generated migration + tests.

## Open Risks & Assumptions

- `settings.AUTH_USER_MODEL` defaults to `auth.User` (not customised in `data_pulse/settings.py`); a future custom user model would require a migration squash
- The Slack SVG icon is a simplified geometric approximation — acceptable for a "Soon" placeholder

## Success Criteria (Summary)

- `/connections/` renders six provider cards with no layout breakage; Slack is non-interactive with a "Soon" badge
- `python manage.py migrate` applies cleanly and `SlackNotification` is queryable
- `python manage.py test monitor` is green with the two new tests added
